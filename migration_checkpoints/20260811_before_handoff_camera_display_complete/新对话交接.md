## 7. Camera Thread 已完成的 FSP Stack

当前 Stack 归属如下喵。

```text
camera_thread
├── IIC Master
│   ├── DTC TX
│   └── DTC RX
└── VIN
    └── MIPI CSI
        └── MIPI PHY
```

IIC1 实例为 `g_i2c_master_for_peripheral`，工作在 Fast Mode，SDA 为 `P511`，SCL 为 `P512`，Symbol 分别为 `SYS_I2C_SDA` 和 `SYS_I2C_SCL` 喵。

IIC 回调为 `g_i2c_master_for_peripheral_callback`，DTC TX 实例为 `g_transfer0`，DTC RX 实例为 `g_transfer1` 喵。

VIN、MIPI CSI 和 MIPI PHY 参数已与单核基线逐项比较通过，VIN 回调已经修正为 `vin_callback` 喵。

摄像头控制驱动已经迁移到 `src\Camera`，当前文件为 `camera_sensor.c/.h` 和 `i2c_control.c/.h` 喵。

驱动只保留本工程实际使用的 1024×600 路径，已经删除 `RES_XXX` 多分辨率枚举、`camera_profiles`、颜色条测试表和颜色比对数组喵。

OV5640 使用板载外部 24 MHz 有源晶振，P501 是废弃引脚，禁止为 P501 增加 XCLK GPIO 或外设输出代码喵。

OV5640 硬复位使用 P709，对应 FSP Symbol 为 `CAMERA_RESET` 喵。

`Camera Thread` 当前依次执行 `i2c_control_init()`、`camera_open()`，成功后设置 `HARDWARE_CAMERA_INIT_DONE` 喵。

RTT 已确认以下完整成功日志喵。

```text
[CAM] Camera Thread started.
[CAM] External active oscillator is used; P501 is not used.
[CAM] Opening IIC master...
[CAM] IIC master opened.
[CAM] Initializing OV5640...
[CAM][OV5640] Waiting for sensor power stabilization.
[CAM][OV5640] Hardware reset on P709 completed.
[CAM][OV5640] Writing sensor configuration table.
[CAM][OV5640] Configuration verified, PCLK=96000000 Hz, FPS=60.
[CAM] OV5640 initialization completed.
[CAM] HARDWARE_CAMERA_INIT_DONE set.
```

该日志证明 IIC、P709 复位、OV5640 寄存器表写入和回读校验、内部时钟计算以及 RTOS 初始化事件均已通过喵。

本轮曾稳定复现 `Verify reg 0x3400 failed, write=0x07, read=0x00`，最终确认不是硬件损坏，也不是上电延迟或整个 IIC/DTC 链路失效喵。

`camera_write_array()` 会对配置表逐项写入并立即回读，故障前已有数十个寄存器通过校验，实际问题是旧配置把 `0x3406[0]` 置为自动 AWB，同时又写入并严格校验 `0x3400～0x3405` 手动 RGB 增益，自动算法可能接管这些动态寄存器喵。

正式版现在使用 `AWB_AUTO_ENABLE (0U)`，配置表只写入 `AWB_MAN_CTRL`，已经删除 `0x3400～0x3405` 的固定手动增益写入，硬件重新验证通过喵。

CPU0 D-Cache 已启用，IIC TX 又由 DTC 搬运，因此 `write_reg_8bit()`、`read_reg_8bit()`、`write_reg_16bit()` 和 `read_reg_16bit()` 的全部 TX 路径均在 `R_IIC_MASTER_Write()` 前调用 `SCB_CleanDCache_by_Addr()`，保证 CPU 生成的发送缓冲区先写回 SRAM 再由 DTC 读取喵。

当前寄存器读取长度均为 1 字节，FSP IIC 驱动不会为该长度启用 RX DTC，所以没有对接收变量盲目执行 Cache invalidate 喵。

此前曾为验证 MIPI/VIN 加入单帧测试，硬件一度成功捕获一帧，但之后按用户要求已经将 `camera_thread_entry.c` 精确恢复到测试前版本；新对话不得假定该临时代码仍在工程中喵。

该日志尚不能证明 MIPI-CSI 收包、VIN 帧完成或 SDRAM 图像缓冲区有效，这正是新对话的下一项验证任务喵。

推荐的最小执行顺序如下喵。

1. 实现 `mipi_csi0_callback()` 和 `vin_callback()`，回调中只记录状态并向 Camera Thread 发布事件，不做图像复制、RTT 大量打印或显示刷新喵。
2. 按单核源工程顺序打开 VIN、准备 FSP 已生成的三个 VIN 缓冲区、进行必要的 D-Cache 维护并启动捕获喵。
3. 最后调用 `camera_stream_on()`，等待一次 `VIN_EVENT_NOTIFY` 且 `frame_complete` 有效喵。
4. 通过 RTT 输出完成帧计数、完成缓冲区地址和错误计数，并用调试器观察该缓冲区数据是否持续变化喵。

本阶段不要加入 AI 预处理、推理、CPU1、IPC、网络或新的抽象层喵。
