# RA8P1 M33多任务与双核协同实施计划书

> 文档日期：2026-08-14  
> 适用工程：`RA8P1_DualCoreProject`  
> 处理器分工：CPU0为Cortex-M85，CPU1为Cortex-M33  
> 文档性质：目标架构、实施顺序、验收标准和新对话交接基线  
> 当前状态：方案讨论稿，尚未依据本计划修改代码

## 1. 文档目的

本文档用于统一后续M33多任务设计、M85实时图传编码、双核IPC、DA16200故障图片上传、nRF遥控与实时图传、电机控制演进等工作的实施边界喵。

本文档同时用于未来新对话或新模型接手工程时快速恢复上下文喵。接手者应先阅读本文，再阅读同目录下的`完整系统集成与移植说明.md`，最后以当前源码、生成文件、链接脚本、MAP文件和硬件日志核对实际状态喵。

本文档不是“所有功能已经完成”的证明喵。凡未经过构建、双核烧录和目标板验证的内容，都只能称为目标方案或待验证实现喵。

## 2. 融合后的总体决策

本次讨论形成以下总体决策喵。

1. DA16200链路具有一次性的M33业务启动放行权喵。
2. M33上电后，除必要安全初始化、IPC基础接收和DA16200启动管理外，其余业务处理先等待系统启动门禁喵。
3. DA16200首次连接成功，或者首次连接总时间超过规定上限后，都必须放行其余M33业务任务喵。
4. 系统被放行后，Wi-Fi掉线不得再次冻结Vehicle、Command RX、IPC或Video TX等任务喵。
5. DA16200在正常运行阶段保持后台任务属性，其优先级低于车辆安全控制、遥控命令接收和IPC交付喵。
6. EventGroup负责启动门禁、链路在线状态和安全锁存等“状态信息”喵。
7. Queue或单槽邮箱负责命令、帧描述符、上传作业和完成结果等“业务数据”喵。
8. Task Notification或二值信号量负责ISR到任务的快速唤醒喵。
9. JPEG载荷不放进Queue或IPC消息，实际数据放在共享SDRAM中，Queue和IPC只传递描述符或短通知喵。
10. 实时图传的黑白JPEG由M85负责采图、缩小和编码，M33只负责校验共享帧并通过nRF发送喵。
11. RTT控制电机仅作为初步测试入口，不能成为正式电机控制架构喵。
12. 正式阶段的上位机遥控器、手持遥控器和自动控制都统一生成`vehicle_command_t`，并通过Vehicle Command Queue交给Vehicle Thread喵。
13. Vehicle Thread是电机、吸附和底盘执行器的唯一软件所有者喵。
14. nRF实时图传在遥控端未准备好时执行有界超时和后台退避探测，不得阻塞其他M33任务喵。

## 3. 系统边界和三条独立业务链路

### 3.1 遥控与车辆控制链路

```text
RTT临时测试 / 上位机遥控 / 手持遥控器 / 自动控制
                         │
                         ▼
                vehicle_command_t
                         │
                         ▼
              Vehicle Command Queue
                         │
                         ▼
                  Vehicle Thread
                         │
               ┌─────────┴─────────┐
               ▼                   ▼
            电机/GPT           吸附/安全控制
```

所有命令来源只能提交统一命令，不得直接调用底层电机或GPT驱动喵。

### 3.2 实时图传链路

```text

        │ 1024x600 RGB565
        ▼

        │ 中心裁剪/降采样/Gray8/JPEG
        ▼

        ▼

```

实时图传执行“最新帧优先”策略喵。任一环节跟不上时丢弃完整旧帧，不积压历史画面喵。

## 4. 启动门禁总体设计

### 4.1 启动阶段划分

M33启动分成三个阶段喵。

#### 阶段A：必要基础和安全初始化

本阶段不能被Wi-Fi阻塞，至少应完成以下内容喵。

- 创建系统EventGroup、Queue、邮箱和必要静态对象喵。
- 将所有电机和吸附输出置于明确的安全停止状态喵。
- 建立IPC中断基础接收能力，或者明确让M85在收到M33 READY之前不发布业务数据喵。
- 初始化DA16200使用的UART和Wi-Fi管理上下文喵。
- 记录启动总截止时间喵。

#### 阶段B：DA16200首次连接窗口

Wi-Fi Upload Thread或专用启动管理逻辑依次尝试喵。

1. 等待DA16200供电稳定喵。
2. 探测AT命令响应喵。
3. 确认或切换到Station模式喵。
4. 连接指定热点喵。
5. 验证Wi-Fi状态喵。
6. 建立到图片接收端的TCP会话喵。

本阶段必须使用覆盖全部步骤的“总启动截止时间”，不能只给热点连接函数设置局部超时喵。

建议初始总启动截止时间设为20至30秒，最终数值必须根据DA16200实测启动时间确定喵。

#### 阶段C：放行业务任务

满足以下任一条件即设置`APP_START_ALLOWED`喵。

- DA16200完成Wi-Fi和TCP连接喵。
- DA16200首次连接总时间超过规定上限喵。

`APP_START_ALLOWED`一旦设置，在本次上电周期内不得清除喵。

### 4.2 为什么不能简单阻塞全部M33代码

如果Vehicle Thread在电机输出尚未归零前等待Wi-Fi，电机状态可能不安全喵。

如果IPC基础接收尚未建立而M85已经发布共享帧，可能出现共享槽占满、旧帧残留或CPU0等待回执超时喵。

因此，本计划中的“其余任务阻塞”特指正常业务循环阻塞，不包括安全输出建立、RTOS对象创建和必要双核握手喵。

## 5. EventGroup规划

建议创建一个M33系统状态EventGroup，初步规划如下喵。

```c
#define SYSTEM_EVENT_APP_START_ALLOWED      (1UL << 0)
#define SYSTEM_EVENT_WIFI_ONLINE            (1UL << 1)
#define SYSTEM_EVENT_WIFI_FRONTEND_READY    (1UL << 2)
#define SYSTEM_EVENT_NRF_VIDEO_ONLINE       (1UL << 3)
#define SYSTEM_EVENT_NRF_COMMAND_ONLINE     (1UL << 4)
#define SYSTEM_EVENT_EMERGENCY_STOP         (1UL << 5)
#define SYSTEM_EVENT_SYSTEM_DEGRADED        (1UL << 6)
```

以上名称为计划级建议，正式实现前需要与现有命名和FSP生成边界核对喵。

### 5.1 启动门禁位

所有正常业务任务在完成自己的最小安全初始化后，等待`SYSTEM_EVENT_APP_START_ALLOWED`喵。

等待时使用`clearOnExit = pdFALSE`，任何业务任务都不能清除启动放行位喵。

### 5.2 动态链路状态位

`WIFI_ONLINE`、`WIFI_FRONTEND_READY`和`NRF_VIDEO_ONLINE`可以随链路状态设置和清除喵。

这些动态状态只能控制对应业务是否发送，不能反向清除`APP_START_ALLOWED`喵。

### 5.3 安全锁存位

`EMERGENCY_STOP`属于高优先级安全状态喵。急停一旦置位，普通遥控命令不得自动清除，必须通过明确的安全恢复流程解除喵。

## 6. Queue、邮箱和Task Notification规划

| 生产者 | 消费者 | 机制 | 携带内容 | 策略 |
|---|---|---|---|---|
| nRF IRQ ISR | Command RX Thread | 二值信号量或Task Notification | 无业务载荷 | 快速唤醒，ISR不做SPI |
| Command RX / RTT /上位机/自动控制 | Vehicle Thread | Vehicle Command Queue | `vehicle_command_t` | 普通命令最新值优先，急停独立锁存 |
| IPC ISR | IPC Thread | Task Notification | 门铃类型或待处理提示 | ISR不读JPEG、不算CRC |
| IPC Thread | Video TX Thread | 单槽视频邮箱加Task Notification | 视频槽号、帧号、长度、CRC | 最新帧优先，不积压 |
| Video TX Thread | IPC Thread | Completion Queue或等价完成邮箱 | 帧号、槽号、成功状态 | 完成后释放共享槽 |
| IPC Thread | Wi-Fi Upload Thread | 长度1的Fault Upload Queue | 故障JPEG描述符 | 不覆盖正在上传的故障图 |
| Wi-Fi Upload Thread | IPC Thread/共享协议 | 完成接口或Completion Queue | 帧号、成功状态、错误码 | 最终释放故障共享区 |

Queue和邮箱只存描述符，不复制大块JPEG喵。

## 7. M33任务规划与优先级

当前优先级顺序总体合理，计划保持如下关系喵。

| 优先级 | 任务 | 核心责任 | 启动门禁行为 | 运行期阻塞点 |
|---:|---|---|---|---|
| 7 | Vehicle Thread | 底盘、吸附、安全停车、控制周期 | 先建立安全输出，再等待放行 | 10ms周期、命令邮箱 |
| 6 | Command RX Thread | nRF遥控接收、校验和命令发布 | 等待放行 | IRQ通知，20ms安全轮询兜底 |
| 5 | IPC Thread | 双核门铃、共享区校验和业务分发 | 基础IPC先就绪，业务分发等待放行 | IPC通知和短周期维护 |
| 4 | Video TX Thread | 黑白JPEG的nRF分包发送 | 等待放行 | 视频邮箱、链路退避定时器 |
| 3 | Wi-Fi Upload Thread | DA16200启动、TCP和故障图上传 | 启动阶段负责放行 | 上传队列和后台重连延时 |

### 7.1 优先级判断

Vehicle Thread优先级最高是正确的，因为车辆安全和控制周期不能被图像链路拖延喵。

Command RX高于IPC和图像任务是正确的，因为遥控停止命令必须低延迟到达Vehicle Thread喵。

IPC高于两个大数据发送任务是正确的，因为共享缓冲区状态和跨核回执需要及时推进喵。

Video TX高于Wi-Fi Upload是合理的，因为实时图传对时效性敏感，而故障图上传可以后台完成喵。

Wi-Fi Upload拥有启动放行权但保持最低业务优先级是合理的喵。启动阶段其他任务都在等待门禁，因此无需提升Wi-Fi任务优先级；进入运行阶段后，低优先级可以防止AT/TCP处理影响车辆控制喵。

### 7.2 最终判断必须依赖目标板测量

优先级数字正确不代表实时性已经被证明喵。后续必须测量Vehicle Thread的10ms周期抖动、Command RX中断到命令入队延迟、IPC共享槽释放时间、Video TX整帧占用时间和各任务栈水位喵。

## 8. M85实时图传编码责任

### 8.1 为什么编码放在M85

实时图传需要读取相机帧、裁剪、降采样、颜色转灰度和JPEG压缩，计算量和存储带宽明显高于M33的发送控制逻辑喵。

M85更适合承担图像预处理和JPEG编码，M33保留给车辆控制、无线通信、IPC管理和故障隔离喵。

### 8.2 目标图像格式

实时图传目标暂定为喵。

```text
输入：1024x600 RGB565相机帧
处理：中心裁剪 + 4x4亮度盒式降采样 + 轻度时域混合
编码输入：200x112 Gray8
编码输出：单通道黑白JPEG
JPEG质量：35
目标发布周期：100ms
```

以上参数来自当前目标说明和已有源码，但最终帧率必须通过实际JPEG大小和nRF吞吐测量确认喵。

### 8.3 M85发布规则

M85 Encode Thread只读取最新相机帧喵。

如果实时视频共享槽没有可写空间，M85应丢弃当前帧，不等待M33释放旧槽喵。

写入顺序必须遵循喵。

```text
选择FREE或允许覆盖的READY槽
  → 标记WRITING
  → 写入JPEG
  → 计算共享副本CRC32
  → 写入帧号、长度、尺寸和CRC
  → Clean D-Cache
  → 标记READY
  → 发送IPC短门铃
```

M85绝不能覆盖M33已经标记为`IN_USE`的槽喵。

### 8.4 M33消费规则

M33 IPC Thread收到视频门铃后选择最新合法READY槽，校验头部、长度、JPEG边界和CRC，再标记为`IN_USE`喵。

Video TX完成或放弃发送后，必须把完成结果交还IPC Thread，由IPC Thread释放对应共享槽喵。

## 9. nRF实时图传离线与重试策略

nRF24不是面向连接的Wi-Fi协议，所谓“遥控端在线”应由带ACK数据包是否收到硬件ACK判断喵。

遥控端尚未准备完成时，Video TX不得永久挂起，也不得持续高频执行50ms超时喵。

推荐状态机如下喵。

```text
UNKNOWN
  │ 发送带ACK探测或START包
  ├── ACK成功 → ONLINE
  └── 超时    → OFFLINE_BACKOFF

ONLINE
  │ 正常发送最新帧
  ├── 成功 → 保持ONLINE
  └── 连续失败 → OFFLINE_BACKOFF

OFFLINE_BACKOFF
  │ 丢弃旧视频帧并立即释放共享槽
  │ 等待500ms至2s退避时间
  └── 再次探测
```

收到一次有效ACK后恢复正常实时发送喵。离线期间不积压旧视频帧喵。

Command RX链路和Video TX链路使用不同SPI、信道和地址，二者的在线状态及故障恢复不能混用喵。

## 10. DA16200启动与运行期重连状态机

建议将DA16200链路划分为以下状态喵。

```text
POWER_WAIT
  → AT_PROBE
  → STA_MODE_CHECK
  → WIFI_JOIN
  → TCP_CONNECT
  → ONLINE
  → BACKOFF
```

### 10.1 首次启动窗口

首次启动窗口受全局截止时间约束喵。任一步骤失败且总时间尚未到期，可以在窗口内重试喵。

连接成功时设置`WIFI_ONLINE`、`WIFI_FRONTEND_READY`和`APP_START_ALLOWED`喵。

总时间到期时设置`SYSTEM_DEGRADED`和`APP_START_ALLOWED`，随后进入后台退避重连喵。

### 10.2 正常运行期

运行期连接失败只影响故障图片上传喵。

Wi-Fi任务应清除相应在线位、关闭失效TCP会话、执行有界延时，然后重新探测喵。

Wi-Fi任务不得清除`APP_START_ALLOWED`，不得挂起Vehicle、Command RX、IPC或Video TX任务喵。

### 10.3 故障上传作业策略

故障共享区当前属于单帧握手资源喵。Wi-Fi未在线时，需要在正式实现前明确采用以下哪一种策略喵。

- 策略A：立即返回上传失败并释放共享区，适合保证系统不悬挂喵。
- 策略B：保留当前故障图，在限定总时间内等待Wi-Fi恢复，适合提高图片送达率，但必须防止长时间占用共享区喵。

本计划推荐使用“限定等待后失败”的折中策略喵。例如故障作业允许等待一个明确的上传总时限，超时后返回错误并释放共享区，不能无限期保留指针喵。

## 11. 电机控制演进计划

### 11.1 当前阶段：RTT初步测试

RTT只用于验证方向、左右轮极性、速度百分比、停车动作和基本Vehicle Service调用喵。

RTT输入必须转换为`vehicle_command_t`并进入Vehicle Command Queue，不允许RTT测试代码直接操作GPT或GPIO喵。

RTT测试入口必须有明确编译开关，正式遥控链路验收后关闭或移除喵。

### 11.2 下一阶段：上位机或手持遥控器

上位机或手持遥控器只负责产生带序号、来源、动作和参数的统一命令喵。

nRF Command RX完成协议、CRC、序号和范围校验后，再将合法命令提交给Vehicle Command Queue喵。

Vehicle Thread保留200ms遥控心跳超时停车机制喵。超时停车应由Vehicle Thread本地判断，不能依赖遥控器继续发送STOP包喵。

### 11.3 最终阶段：自动控制

自动控制算法可以根据IMU、传感器或任务状态生成`vehicle_command_t`，但仍不能直接控制电机喵。

自动控制和人工遥控之间必须有显式模式状态机喵。建议至少包含喵。

```text
MANUAL
AUTOMATIC
EMERGENCY_STOP
FAULT
```

### 11.4 命令仲裁原则

推荐优先级如下喵。

```text
急停和硬件故障
    >
人工遥控STOP及人工接管
    >
人工方向/速度命令
    >
自动控制命令
    >
RTT调试命令
```

普通命令可以使用“最新目标覆盖旧目标”策略，但急停不能被普通命令覆盖喵。

## 12. 故障处理和降级原则

| 故障 | 影响范围 | 不允许发生的行为 | 推荐处理 |
|---|---|---|---|
| DA16200无响应 | 故障图上传 | 永久阻塞全部M33任务 | 启动总超时后放行，后台重连 |
| 热点不可用 | 故障图上传 | 停止车辆控制或实时图传 | 清在线位，退避重试 |
| TCP接收端不可用 | 故障图上传 | 无限持有共享故障图 | 限时等待或明确失败回执 |
| 遥控端图传未上线 | 实时图传 | 旧帧持续积压 | 丢旧帧、释放槽、退避探测 |
| 遥控命令心跳丢失 | 车辆控制 | 保持上次运动无限运行 | 约200ms本地安全停车 |
| IPC门铃丢失 | 图像链路 | 仅依赖一次中断 | 任务周期检查共享状态作为兜底 |
| JPEG CRC错误 | 对应图像 | 继续发送损坏帧 | 标记错误、释放资源、记录一次错误 |
| Queue满 | 对应业务 | 静默覆盖关键数据 | 按业务策略丢帧或返回错误 |

## 13. 日志和可观测性

RTT日志只保留以下信息喵。

- 任务或外设初始化完成喵。
- DA16200首次连接结果和运行期状态变化喵。
- nRF链路ONLINE/OFFLINE状态变化喵。
- 故障图片上传成功或最终失败喵。
- 视频帧周期统计摘要，而不是每个分包日志喵。
- 车辆安全停车、急停和故障喵。
- IPC协议、CRC、超时和共享状态错误喵。
- 各任务栈水位和周期抖动的低频统计喵。

禁止在正常路径高频输出每帧、每包或每个控制周期日志喵。

## 14. 分阶段实施与验收顺序

必须一次只推进一个阶段，并在通过验收后再进入下一阶段喵。

### 阶段0：计划确认与当前基线冻结

工作内容喵。

- 确认本文档中的启动门禁、优先级、链路分工和电机演进方向喵。
- 检查当前工作树和最新硬件日志喵。
- 明确临时测试代码和正式业务代码边界喵。

验收标准喵。

- 用户确认计划无方向性遗漏喵。
- 未修改任何正式源码或FSP配置喵。

### 阶段1：M33安全启动和EventGroup门禁

工作内容喵。

- 创建系统状态EventGroup喵。
- 建立电机安全初始状态喵。
- 让业务任务在最小初始化后等待`APP_START_ALLOWED`喵。
- 建立DA16200首次连接总截止时间喵。

验收标准喵。

- Wi-Fi正常时，连接成功后其余任务启动喵。
- DA16200断电或热点关闭时，到达总超时后其余任务仍能启动喵。
- 超时放行后Wi-Fi任务继续后台重连喵。
- Wi-Fi再次掉线不会冻结已运行任务喵。

### 阶段2：RTT电机最小闭环

工作内容喵。

- RTT测试输入转换成统一车辆命令喵。
- 通过Vehicle Command Queue交给Vehicle Thread喵。
- 保证Vehicle Thread是执行器唯一所有者喵。
- 验证急停锁存和超时停车喵。

验收标准喵。

- 架空车轮测试前进、后退、左转、右转和停止喵。
- 任何测试结束都能回到明确停车状态喵。
- RTT断开不会保持车辆持续运动喵。

### 阶段3：nRF遥控命令闭环

工作内容喵。

- Command RX使用IRQ通知和有界轮询兜底喵。
- 校验命令协议、序号、CRC和参数范围喵。
- 将合法命令提交给Vehicle Command Queue喵。
- 保留200ms心跳超时停车喵。

验收标准喵。

- 手持遥控指令能够控制车辆喵。
- 松手STOP丢包时，后续心跳或本地超时仍能停车喵。
- 遥控器掉电后车辆约200ms内停车喵。

### 阶段4：M85黑白JPEG实时编码和双核发布

工作内容喵。

- 在M85完成200x112 Gray8和JPEG质量35编码喵。
- 使用实时视频共享区双槽发布喵。
- M33校验并正确管理`READY/IN_USE/FREE`喵。

验收标准喵。

- 固定JPEG先通过共享区和CRC验证喵。
- 实际相机JPEG能够持续跨核发布喵。
- M33繁忙时M85丢弃旧帧而不是阻塞喵。
- 两核不存在覆盖`IN_USE`槽的情况喵。

### 阶段5：nRF实时图传和离线退避

工作内容喵。

- Video TX发送START、DATA和END喵。
- 遥控端完成接收、整帧CRC、JPEG解码和LVGL显示喵。
- 实现遥控端离线时的后台退避探测喵。

验收标准喵。

- 遥控端未启动时，Vehicle、Command RX、IPC和Wi-Fi任务继续运行喵。
- 遥控端上线后能自动恢复最新帧显示喵。
- 离线期间不积压旧视频帧喵。

### 阶段6：故障图片DA16200上传闭环

工作内容喵。

- M85 AI触发彩色故障JPEG喵。
- M33校验共享JPEG并投递Fault Upload Queue喵。
- DA16200发送到本地网页接收器喵。
- 明确上传失败和超时释放策略喵。

验收标准喵。

- 网页收到的帧号、尺寸、长度、JPEG边界和置信度正确喵。
- 上传期间实时图传和车辆控制继续工作喵。
- Wi-Fi中断后不会无限占用故障共享区喵。

### 阶段7：全系统并发压力验证

工作内容喵。

- 同时运行车辆遥控、实时图传、AI检测和故障上传喵。
- 注入热点断开、遥控端掉电、CRC错误和IPC超时等故障喵。

验收标准喵。

- 连续运行至少10分钟无死锁、栈溢出和共享区所有权错误喵。
- Vehicle Thread控制周期满足实测要求喵。
- 遥控命令安全超时始终有效喵。
- Wi-Fi和视频链路故障不会扩散到车辆控制喵。

## 15. 实施边界

在用户明确授权进入某个阶段前，不得跨阶段大范围修改代码喵。

不得未经授权修改FSP、`configuration.xml`、生成文件、链接脚本或安全分区喵。

临时测试代码必须隔离并可清除，验收后按用户要求删除喵。

所有正式协议结构必须在M85和M33两侧保持字节级一致喵。

任何涉及共享SDRAM的修改都必须同时核对地址、长度、对齐、Cache维护、状态所有者和MAP证据喵。

## 16. 新对话或新模型交接摘要

接手者应理解以下事实和目标喵。

1. 当前目标不是单独完成某一个外设，而是构建M85图像处理加M33实时控制与通信的双核系统喵。
2. M85负责相机、AI和实时图传JPEG编码，M33负责车辆控制、nRF通信、IPC消费和DA16200上传喵。
3. DA16200拥有一次性启动放行权，但运行期优先级低于车辆安全任务喵。
4. 首次Wi-Fi连接成功或全局启动超时都必须设置`APP_START_ALLOWED`喵。
5. 系统放行后Wi-Fi只在后台重连，不能再次冻结其他任务喵。
6. EventGroup负责状态，Queue/邮箱负责数据，Task Notification或信号量负责中断唤醒，共享SDRAM负责JPEG载荷喵。
7. 实时视频使用200x112黑白JPEG、最新帧优先和共享双槽喵。
8. 故障图片使用独立共享区和单帧握手，交给DA16200上传喵。
9. RTT电机控制只是初期验证喵。未来上位机遥控器、手持遥控器和自动控制都必须统一进入Vehicle Command Queue喵。
10. Vehicle Thread是电机和吸附执行器的唯一所有者，急停和遥控超时停车不能被图像或网络任务影响喵。
11. 当前M33优先级`Vehicle 7 > Command RX 6 > IPC 5 > Video TX 4 > Wi-Fi 3`方向合理，但必须通过目标板数据验证喵。
12. 遥控端图传未完成时，nRF Video TX应有界超时、释放旧帧并后台退避探测喵。
13. 本文档当前只是方案基线，尚未据此修改代码喵。
14. 下一步应先让用户确认本文档，然后只从阶段1开始实施，不能同时展开所有功能喵。
