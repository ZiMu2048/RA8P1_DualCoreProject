# 巡检车—遥控器完整系统集成与移植说明

## 1. 本次实现的系统边界

本次改动同时覆盖两个工程：

- 巡检车：`RA8P1_DualCoreProject`，CPU0 为 Cortex-M85，CPU1 为 Cortex-M33。
- 遥控器：`Renesas_Cup_Final_Game` 的独立分支 `codex/full-system-integration`，基于 `origin/master_1`。

三条数据链路彼此独立：

1. **遥控命令**：遥控器 SPI1/NRF24 → 车端 SPI0/NRF24 → M33 Command RX → Vehicle 控制。
2. **实时图传**：车端 M85 采图和压缩 → IPC 共享内存 → M33 SPI1/NRF24 → 遥控器 SPI0/NRF24 → JPEG 解码 → LVGL。
3. **故障图片**：车端 M85 AI 判定与 JPEG → IPC 共享内存 → M33 → DA16200 → 本地网页。

IPC **不传车辆状态**。车辆状态若需要上传，应走车端 NRF 到遥控器的无线链路。

## 2. 为什么选择 200×112 灰度 JPEG

480×272 RGB888 原始一帧为：

```text
480 × 272 × 3 = 391680 字节
```

NRF24 的空中速率虽然配置为 2 Mbps，但还包含前导码、地址、CRC、包间隔和重发开销。直接传原始 RGB888 无法得到有用帧率。因此采用：

```text
1024×600 RGB565 相机帧
  → 中心裁剪 + 4×4 亮度盒式降采样
  → 200×112 Gray8
  → 单通道 JPEG，质量 35
  → 32 字节 NRF 分包
  → 遥控器解码并放大为 480×272 RGB888
```

这样“480×272 RGB888”是遥控器最终显示缓存的格式和尺寸，无线链路传输的是压缩 JPEG。代码采用最新帧优先策略：编码、IPC、解码任一环节跟不上时丢整帧，不积压旧画面。实际帧率受场景 JPEG 大小、射频环境和模块质量影响，应通过 RTT 统计再调节。

主要调节位置：

- 编码周期：CPU0 `src/encode_thread_entry.c` 中的 100 ms 周期。
- JPEG 质量：同文件中的质量 35。
- 图传信道：车端 `video_radio.c` 与遥控器 `wireless_touch_tx.h` 的信道 100。

## 3. 最终线程规划

FreeRTOS 数字越大，优先级越高。

### 3.1 车端 CPU0（M85）

| 优先级 | 线程 | 责任 | 交互方式 |
|---:|---|---|---|
| 7 | IPC Thread | 故障 JPEG 的 IPC 通知和完成回收 | 共享内存、IPC 门铃 |
| 6 | Display Thread | 本地屏幕与 AI 标注显示 | 图像邮箱/显示接口 |
| 5 | AI Thread | 故障检测与结果发布 | 相机帧邮箱、故障上传邮箱 |
| 4 | Encode Thread | 实时图传降采样、JPEG 编码、发布最新帧 | 相机帧邮箱、视频共享内存 |
| 3 | Camera Thread | MIPI/VIN 采集并发布最新帧 | 相机帧邮箱 |

Encode Thread 使用 8192 字节栈。原因是 JPEG 编码和局部变量比普通控制线程重；它不能高于 IPC/显示等关键交付线程，也不能低到长期没有 CPU 时间。

### 3.2 车端 CPU1（M33）

| 优先级 | 线程 | 责任 | 交互方式 |
|---:|---|---|---|
| 7 | Vehicle Thread | 执行底盘/吸附控制、超时安全停车 | Vehicle Command Queue |
| 6 | Command RX Thread | 等待 P705/IRQ19，读 SPI0 NRF 命令并校验 | ISR 信号量、命令队列 |
| 5 | IPC Thread | 接收两类 IPC 门铃，管理故障/实时图共享内存 | IPC、两个邮箱 |
| 4 | Video TX Thread | 从视频邮箱取 JPEG，SPI1 NRF 分包发送 | Video Frame Mailbox |
| 3 | WIFI Upload Thread | 把故障 JPEG 通过 DA16200 上传网页 | Fault Upload Mailbox/UART |

Vehicle 和 Command 的安全控制高于大数据传输。Video TX 与 Wi-Fi 分开，防止 DA16200 的 AT/TCP 等待阻塞实时图传。

### 3.3 遥控器

| 优先级 | 线程 | 责任 | 交互方式 |
|---:|---|---|---|
| 7 | Command TX Thread | 每 50 ms 发送按键状态心跳 | 命令 TX 环形队列 |
| 6 | Video RX Thread | P705/IRQ19 唤醒、排空 RX FIFO、组帧和 CRC32 | IRQ 通知、JPEG 暂存区 |
| 5 | Display Thread | LVGL、GT911 轮询、提交完整 RGB888 帧 | 显示 pending 标志 |
| 4 | JPEG Decode Thread | 解码 200×112 灰度 JPEG 并放大到 480×272 RGB888 | Task Notification |

原 Touch Thread 几乎空转，因此改作 JPEG Decode Thread。GT911 仍由 LVGL 输入设备在 Display Thread 内轮询，避免两个线程同时调用 LVGL。

## 4. 线程交互和运行流程

### 4.1 遥控命令

1. LVGL PRESSED/RELEASED 回调调用 `WirelessTouchTx_Send()`。
2. Command TX Thread 每 50 ms 调用 `WirelessTouchTx_SendHeartbeat()`：按住方向时重复当前方向，松手时重复 STOP。
3. 遥控器 SPI1 NRF：信道 76、地址 `CMDRX`、2 Mbps、8 字节控制包。
4. 车端 P705/IRQ19 下降沿只释放信号量，不在 ISR 内做 SPI。
5. Command RX Thread 排空最多 3 个 RX FIFO 包，做魔数、协议、动作、数值与 CRC 校验。
6. 合法新序号命令进入 Vehicle Command Queue。
7. Vehicle Thread 执行运动或吸附命令；若 200 ms 没有新的遥控心跳则安全停车。

这样即使“松开”包丢失，后续 STOP 心跳仍可停车；若遥控器掉电，车端 200 ms 超时也会停车。

### 4.2 实时图传

1. Camera Thread 发布最新相机帧。
2. CPU0 Encode Thread 每 100 ms 读取最新帧，降采样、时域 3:1 混合并编码 JPEG。
3. CPU0 把 JPEG 写入实时视频共享内存双缓冲槽并发送 IPC 门铃。
4. CPU1 IPC Thread 选择最新 READY 槽，标记为 IN_USE，并发布 Video Frame Mailbox。
5. Video TX Thread 通过车端 SPI1 NRF 发送 START、DATA、END。
6. 遥控器 Video RX Thread 通过 SPI0 收包，检查元数据和整帧 CRC32。
7. 完整帧复制到稳定解码区并通知 JPEG Decode Thread；解码忙则丢弃这一帧。
8. JPEG Decode Thread 输出下一块 480×272 RGB888 缓冲并通知 GUI。
9. Display Thread 在 LVGL 上下文中替换显示内容。
10. 车端 Video TX 完成后，经 CPU1 IPC Thread 将共享槽释放为 FREE。

### 4.3 故障图片上传

原故障图片流程保留：CPU0 AI/上传工作线程生成故障 JPEG，写入故障共享区；CPU1 IPC Thread 校验后交给 WIFI Upload Thread；DA16200 通过 TCP 发送到本地网页。实时视频和故障图片使用不同共享区、不同状态机，互不覆盖。

## 5. IPC 共享内存布局

共享窗口仍位于 SDRAM 顶端，结尾固定为 `0x70000000`：

| 用途 | 起始地址 | 大小 | 说明 |
|---|---:|---:|---|
| 故障 JPEG | `0x6FFE0000` | `0x11000` | 单帧握手，容量覆盖现有 64 KiB 故障图 |
| 实时视频 | `0x6FFF1000` | `0x0F000` | 64 字节头 + 两个 30688 字节槽 |

实时视频槽状态为 FREE → WRITING → READY → IN_USE → FREE。CPU0 可覆盖旧 READY 槽，但绝不覆盖 CPU1 正在使用的 IN_USE 槽。

两核都必须对共享区执行 D-Cache clean/invalidate；只用 `volatile` 不能替代缓存维护。

## 6. NRF 配置和接线

### 6.1 车端

| 链路 | SPI | MISO/MOSI/SCK/CSN | CE | IRQ | 信道/地址 |
|---|---|---|---|---|---|
| Command RX | SPI0 | P700/P701/P702/P703 | P704 | P705/IRQ19 | 76 / `CMDRX` |
| Video TX | SPI1 | P100/P101/P102/P103 | P104 | 不使用 | 100 / `VIDEO` |

CSN 由 SPI SSL 外设自动控制。

### 6.2 遥控器

| 链路 | SPI | MISO/MOSI/SCK/CSN | CE | IRQ | 信道/地址 |
|---|---|---|---|---|---|
| Video RX | SPI0 | P700/P701/P702/P703 | P704 | P705/IRQ19 | 100 / `VIDEO` |
| Command TX | SPI1 | P709/P708/P415/P414 | P104 | 不使用 | 76 / `CMDRX` |

两端 P705 均配置为输入、上拉、IRQ19、下降沿、数字滤波。GT911 的 P111 不再占用 IRQ19，改为普通上拉输入并由 LVGL 轮询。

## 7. 视频无线协议

每个 NRF 包固定 32 字节：

- START：帧号、版本、源尺寸 200×112、JPEG 长度、CRC32、分片数、编码类型和 XOR 校验。
- DATA：byte 0 为魔数，byte 1 为类型，byte 2..3 为分片号，byte 4..31 为 28 字节 JPEG 数据。
- END：帧号、分片数、总长度、CRC32 和 XOR 校验。

DATA 不再放软件 XOR，因为 32 字节已全部用于头和 28 字节数据；包级错误由 NRF 两字节硬件 CRC 检出，漏包/错序由分片号检测，整帧由 CRC32 检出。

## 8. XML/FSP 配置修改

车端 CPU1：

- 外部中断实例改为 `g_external_irq19`，channel 19，回调 `nrf24_command_irq_callback`。
- P705 绑定 IRQ19；删除旧 P105/IRQ0 绑定。
- CPU1 安全分区取得 P100..P104、P700..P705，避免 CPU0 抢占两路 NRF 引脚。
- 线程优先级按第 3.2 节配置。

车端 CPU0：

- Camera=3、Encode=4、AI=5、Display=6、IPC=7。
- Encode 栈为 8192 字节。

遥控器：

- 删除 `g_external_irq0`，保留 `g_external_irq19` 并绑定 NRF 回调。
- P705=IRQ19 输入上拉；P111=普通输入上拉。
- `configMAX_PRIORITIES=8`，并启用 `configCHECK_FOR_STACK_OVERFLOW`（AWS 生成配置为 1，FSP RTOS 配置为 2）。
- 已存在 `vApplicationStackOverflowHook()`，因此不会再出现缺少 Hook 的链接错误。
- 四线程名称、栈和优先级按第 3.3 节配置。

每次手动修改 `configuration.xml` 后，都要在 e² studio 中执行 **Generate Project Content**。原因是 `ra_gen`、`ra_cfg`、vector 和安全归属文件是 XML 的派生物，只改其中一侧会在下一次生成时被覆盖或造成 XML/代码不一致。

## 9. 构建和烧录顺序

双核工程使用 Smart Bundle，CPU1 工程引用 CPU0 生成的 `.sbd`：

1. 先 Generate 两核工程。
2. 先构建 CPU0。
3. 再构建 CPU1；或者直接构建整个 Solution，让依赖关系自动处理。
4. 使用双核启动组同时下载/调试两核。

CPU0 的 `hal_warmstart.c` 已负责释放/启动 CPU1。调试时 CPU1 在入口暂停属于正常现象；启动组应先让 CPU0 完成系统和安全配置，再放行 CPU1。

遥控器工程在独立工作区导入后，先 Generate Project Content，再 Build Debug。

## 10. 分阶段硬件验证

不要第一次就同时测试三条链路。推荐顺序如下：

1. **命令安全测试**：不装轮或架空，确认 RTT 每 50 ms 收到命令；拔掉遥控器电源，车轮应在约 200 ms 内停下。
2. **双 NRF 寄存器测试**：两端分别读取 STATUS/RF_CH/CONFIG，确认 SPI0 和 SPI1 不互相影响。
3. **固定 JPEG 测试**：先发送一张固定 200×112 JPEG，遥控器必须出现 `[IMG CHECK] PASS` 和 `[JPEG DEC] PASS`。
4. **实时相机测试**：观察编码大小、编码耗时、整帧耗时和丢帧计数；先在近距离、最低发射功率验证，再逐渐增加距离。
5. **故障图片测试**：触发一张故障图，确认实时图传仍继续、网页收到的 JPEG CRC/长度正确。
6. **并发压力测试**：持续遥控、实时图传和故障上传至少 10 分钟，记录各线程 stack high-water mark、命令超时、NRF 重发/丢帧和 IPC CRC 错误。

若图传不稳定，调优顺序为：先降低 JPEG 质量或编码频率，其次检查 3.3 V 去耦、电源峰值和天线距离，最后再换信道。不要先删掉 CRC 或安全超时。
